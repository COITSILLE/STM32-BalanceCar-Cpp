# STM32-BalanceCar-Cpp
# **简介**
STM32F302平衡小车。C和C++混合编写，基于HAL库
几乎所有轮子都是自己造的

控制结构：
```
          转向环---|
                   |---->pwm
速度环--->直立环---|
```

项目一开始是在STM32F103上开发的，所以程序主体（app文件夹里的和app_main.c）没有用到任何302特有的外设。而且两个系列是完全compatible的，主要区别在于STM32F302有FPU。关于为什么FPU比较重要下文会详细讨论。
之所以用C++是因为用C写面向对象太憋屈太不美观了
# **使用的模块、芯片**
1. STM32F302CBT6
2. STM32F103C8T6最小系统板；上面的F103手动换成F302
3. TB6612 FNG模块
4. MPU6050模块
5. SSD1315 OLED模块
6. 12V锂电池组
7. WHEELTEC MG310电机
8. SY8120IABC DCDC芯片
9. ME6251C33M5G LDO芯片

# **用到的软件工具**
1. STM32CubeMonitor
2. VOFA+
    
# **一些经验**
## 一. 原则
   1. **不要对小车抱太大期望** 尤其是对使用的扭矩不大的有刷电机、只有常规的直立环和速度环的小车来说，“平衡”决不是说定在一点。从网上资料和别的大佬的成果展示来看，能做到不倒下、稳在一小段距离来回摆就已经是很好的效果了
   2. **决定最终效果的，远不只是几个PID参数** 有太多因素可以影响整个系统的状态，如果你发现怎么调参都稳不下来就别调了。后面会从个人调试经验出发对此详细展开  

## 二. 经验 
   ### 关于调参步骤
   - 最好设置一个按键切换调试状态，在小车失控时能一按就停掉电机驱动芯片（STBY置0），以免芯片烧毁（你猜为什么提这个）
   - 清零所有PID参数、设置合理的输出限幅和积分限幅
   - 调直立环，先调比例项，不够时小车没啥力，放手就会大角度冲出去，再加大至出现如下现象：松手低频大幅摆动乃至失控倒下（这时要赶紧扶起来）；尝试按住则几乎按不住，在手里高频小幅摆动一段时间才稳下来；手动立起来倾斜一点角度，能感受到很明显的反方向的力。接着还可以略调大一点比例项再开始调微分项。   
   微分项过小，上述的低频大幅摆动仍存在，再加大至出现如下现象：松手高频小幅摆动，且能立着几秒至十几秒才冲出去，不倒下
   - 调成这样后，直立环参数各乘0.6（似乎是某种祖传的“工程经验”，但也确实有效），一般这个时候小车就没有严重的摆动了，但会较前面力气小，且松手后一会儿会带大倾角冲出去
   - 调速度环，比例项是积分项的200倍（同上）。不够时还是会冲出去。继续增大，可能会出现一点低频震荡，这时可将直立环的微分项略调大一点抑制。再加大至小车不再冲出去，而是在一小段距离（几厘米）内来回移动，就大功告成
   如果发现速度环无论怎么调大小车还是冲出去，而且冲出去基本是同一个方向，倾角也不是像只有直立环时冲出去那么大，这种大概率是平衡点没校准好。只需把IMU的平衡点往反方向微调即可消除此问题。
   ### 关于速度环的极性
   - 这一点很多教程强调，但如果你找AI求证，很容易被绕晕。简单说，**速度环的极性应当是“越快越要更快”**。只有直立环时，小车很容易进入一种“带倾角、但相对地面速度不为 0”的平衡，表现为直立一会儿就冲出去。无论串级还是并级，速度环作为直立环的辅助，都需要在检测到速度偏差时给出更大的速度，让加速的过程把车体“推回”到真正的速度为 0 的稳态，从而消除我们不想要的带倾角的平衡。

   ### 关于一些重要算法
   #### 微秒级时间测量 
   有两种方案：
   - 使用一个定时器，配置为1us计数一次到1000为止，配合HAL_GetTick()实现微秒级时间戳。  
      这种方法好在直观、简单，时间戳可以直接用整型，间隔一减就好，缺点是引入定时器的性价比不太高。  
   - Cortex-M3以上内核都集成一个DWT（Data Watchpoint and Trace，数据观察点与跟踪）组件，其中有一个32位计数器CYCCNT，直接挂在系统时钟上，不受任何中断影响。在常用的72MHz主频下，精度可达13.9ns，完全够用。  
   计算可知，连续计数约60s，CYCCNT就会溢出再从零开始。60s对于一般的离散积分、微分需要的时间间隔已经足够。但为了解决超过60s不调用会短暂出错的问题，可以额外在时间戳里记录uwTick（本质是systick）。  
   这种方法好在精度高、稳定，缺点在如果额外记录uwTick，时间戳就得是结构体，取间隔也得单独写函数转换和判断。  
        
   本项目使用了后者，Core/app/slibs/dwt_ustime.h

   #### 调试打印浮点数 
   - STM32 的 C 库为嵌入式环境做了精简，默认不支持 printf 浮点数。在编译选项中添加“-u _printf_float"可以启用被阉割的相关库来打印浮点数，但也确实会让代码体积增加10KB左右。如果追求优化代码体积，可以尝试自己实现浮点数转字符串。   
   - 本项目就是如此，Core/app/slibs/sstrtotype.c 实现了简单的浮点数转字符串函数joinf；另外也简单实现了一些\<stdlib\>的功能以避免引入这个略大的库。  

   #### 测速原理  
   - 鉴于平衡小车正常运行的轮子转速不大，推荐使用T法，即记录脉冲之间的时间间隔。   
   - 本项目的Core/app/drivers/encoder.cpp实现了T法测速，并参考https://www.bilibili.com/video/BV1HLFzeKEVL 进行了改进。 

   #### 姿态角结算
   - 常见的教程直接调用mpu6050的DMP数据，但据说会有10ms的延迟。  
   - 为了拓展性，本项目的Core/app/imu 没有调mpu6050的DMP库，而是尝试写了一个imu的基类，在基类中实现欧拉角解算算法。  
  
   #### 多任务、非阻塞
   - 本项目写在Core/app/slibs/dwt_ustime.h 的宏NON_BLOCK_DELAY(t)实现的非阻塞的延迟，再编写各任务的函数在主循环里一直调用，没到时间就跳过。   
   这种方法好在十分简单，缺点是非常容易受中断等影响。这一点会在下文详细讨论。

   ### 关于姿态传感器噪声  
   - 建议开启mpu6050自带的数字低通滤波器（配置DLPF_CFG寄存器末三位为1~6，具体见手册或问AI）  
   - 互补滤波系数应该是**陀螺仪的权重远高于加速度**（例如0.95），以兼顾高频噪声抑制与细节保留。 

   ### 关于编码器
   - 如果你和我一样使用外部中断捕获脉冲，记得检查GPIO口配置的边沿和你计算公式里的系数匹不匹配。比如说不要只配置了上升沿触发，但公式里每周期边沿数却不是1。一般来说触发频率越高越精准，但也会引入更多噪声。
   - 最好滤一下波。 

   ### 关于PID
   - 串级还是并级？串级是指速度环输出期望倾角作为直立环的设定值，并级是指速度环也输出期望电压/转速/...，叠加到直立环的输出上。两种都用得很广泛，比如说经典的平衡小车之家就是串级的，而B站上有的调参教程，判断速度环极性时让你把直立环参数设为0，给速度环参数，直接看轮子怎么转的，就是并级的。  
   本项目开发过程中两种都试过。简单说，单平衡是并级更容易调，但如果要控制前进后退就容易两个环吵架，表现为前进时不停点头，而串级就不会有这个问题。
   - 平衡小车的直立环是一个PD控制器，反馈是俯仰角。问题在于微分项会对俯仰角进行离散微分，而俯仰角本身大部分是角速度离散积分的结果，这样对积分结果微分会放大噪声，表现为调直立环时，在只有比例项低频大幅摆动后，加微分项摆动仍不被抑制。因此本项目的Core/app/slibs/pid.cpp 的getOutput函数直接允许传入反馈的微分值（在这里就是imu给的角速度）以避免，亲测十分有效
   - 这种做法的问题是预设了PID的设定值是0（误差 = 设定值 - 反馈值，只有设定值是0才能直接用反馈值替代误差），并级问题不大，串级就不行了。解决办法就是对设定值单独微分一下（求导法则\(a+b\)'=a'+b'）

   ### 关于多任务的实现
   使用上述的方法实现多任务，后面的任务即使时间到了也得等前面的任务执行完才轮到自己，且中断处理也会打断整个循环。若存在耗时的任务或中断回调，高频率执行的任务（如计算PID）会很不稳定，表现为小车反应迟钝、调参效果不明显。因此，必须尽力优化每个任务的执行时间。优化过程中，可以调用微秒级时间库测量任务的实际执行时间和实际执行间隔，由上位机监控。本项目开发时做了如下方面的优化，可供核对和参考：    
   - **读取IMU数据**。阻塞的I2C通信实际上非常非常慢，实测完整读一次mpu6050的数据需要近500us，无论在中断读取还是在任务中读取，都会严重拖慢其他任务，更不用说还要处理数据   
   解决方法是使用中断或DMA读取
   - **调试信息**。调参时能实时看姿态角、期望转速等有很大帮助，可以通过OLED显示或串口发送。但如上述，阻塞的显示/发送也是非常耗时的
   解决方法一样，使用中断或DMA发送，或者干脆在小车运行时关闭比较耗时的OLED显示。
   - **IMU数据处理、姿态角解算速度**。这个其实是小问题，如果你追求进一步优化可以看看。  
   在没有FPU的STM32F103，实测一次浮点除法需要约2us，而一次标准库的atan2函数需要约21us
   三角函数慢的解决办法是自己写一个更快的数学库。本项目Core/app/slibs/smath.c 利用查表、近似等手段实现了快速的常用三角函数算法，可以将F103上atan2函数的执行开销降到13us左右，精度也还不错
   如果追求更激进的优化，可以换到有FPU的Cortex-M4，实测一次浮点除法约0.3us，而除了atan略快几us外，smath.h所有函数都比math.h稍慢，而且精度本身不如。项目代码中仍保留smath.h的函数是为了方便直接移植到没有FPU的MCU上，并且也做了兼容。
